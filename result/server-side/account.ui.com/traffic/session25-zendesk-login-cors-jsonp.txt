### 1c. Following the Zendesk hop — return_to is NOT honored (normalized to help.ui.com)
$ curl -sS -D - -o /dev/null -H 'Cookie: <zendesk shared session>' 'https://ubnt.zendesk.com/access/jwt?jwt=<JWT>&return_to=https%3A%2F%2Fevil.com'
HTTP/2 302
location: https://help.ui.com/access/return_to?challenge=<...>&locale=en-US-x-1&return_to=https://help.ui.com/hc
=> Open redirect / javascript: NOT achieved. Zendesk discards the supplied return_to.
=> Response is a 302 with no body; the JWT only lives in the Location header.

### 1d. CORS on the 302 (known *.ui.com reflection, but Location not readable cross-origin)
$ curl -sS -D - -H 'Origin: https://evil.ui.com' -H 'Cookie: UBIC_AUTH=<A>' '.../zendesk_login?...&return_to=https%3A%2F%2Fevil.ui.com'
HTTP/2 302
access-control-allow-credentials: true
access-control-allow-origin: https://evil.ui.com
location: https://ubnt.zendesk.com/access/jwt?jwt=<JWT>&return_to=...
=> fetch(..., {redirect:'manual'}) returns an opaque redirect (status 0, headers hidden);
   redirect:'follow' lands on ubnt.zendesk.com/help.ui.com which do not grant CORS.
   JWT is NOT readable via the *.ui.com CORS primitive. Not exploitable.
